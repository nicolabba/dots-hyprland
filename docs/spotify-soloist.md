# Native Spotify sidebar: Soloist backend

The `feature/spotify-sidebar` branch contains the complete sidebar feature in milestones. This document currently covers the windowless playback service and updater; native sidebar UI and browsing integration follow on the same branch.

## Requirements and setup (opt-in)

Linux x86_64, Python 3.10+, systemd user session, PipeWire or PulseAudio, and a Spotify Soloist API key generated by a Premium account. The graphical-session.target must be managed by your desktop (Illogical Impulse/Hyprland already does this).

Generate your own key at https://developer.spotify.com/dashboard/soloist. Save only the key in `~/.config/spotify-sidebar/soloist-api-key`, owned by you with permissions `0600`, inside a private directory. Never commit or paste the key into chat/issues. No key is distributed with these dotfiles.

From the repository, explicitly opt in:

```sh
./dots/.local/bin/ii-soloist setup
```

This deploys only this integration, downloads an official Soloist binary when absent, enables `ii-soloist.service` with the graphical session, and enables the daily update timer. It does not run the whole desktop installer, enable system services, open windows or modify the firewall. Re-running setup preserves pairing, does not restart an already-active service, and updates the integration scripts/units.

A manually launched test daemon must first be stopped while paused. Setup refuses to run over a live unmanaged pid file. Never print Soloist's full command line: Spotify currently requires the key as an argument, so same-user/root process inspection can reveal it. Loading a private key file avoids shell-history, source-code and unit-file exposure but cannot remove this upstream argv limitation.

## Pair once

Select **Sidebar Spotify** in the native Spotify app on the same LAN. Pairing lives at `~/.local/share/spotify-sidebar/soloist-data`; leave that directory intact across restarts and updates. Soloist then restores the saved session without a phone connection. It starts paused and does not automatically take over another Connect device.

Control locally (no Spotify desktop app required after pairing):

```sh
~/.local/share/spotify-sidebar/soloist/soloist ctl status --data-dir ~/.local/share/spotify-sidebar/soloist-data
~/.local/share/spotify-sidebar/soloist/soloist ctl play --data-dir ~/.local/share/spotify-sidebar/soloist-data
~/.local/share/spotify-sidebar/soloist/soloist ctl pause --data-dir ~/.local/share/spotify-sidebar/soloist-data
```

The widget control WebSocket listens on **127.0.0.1 only**, with a dynamic port stored in that data directory. This is separate from Soloist's LAN-facing Connect discovery/pairing endpoint. Localhost is not a per-user authentication boundary; do not expose this API to the LAN.

### Discovery and firewalls

First-time pairing uses mDNS (`_spotify-connect._tcp`, UDP 5353) and the TCP port advertised in its TXT/SRV records (`CPath=/zc`). Use `avahi-browse -rtp _spotify-connect._tcp` to inspect it. That TCP port can change on restart. Permit only the required local-network sources/ports if needed; do not disable the firewall or copy a temporary test port into a permanent rule. No permanent firewall exception is installed. Stored pairing restored after reboot without additional rules in the feasibility test.

## Automatic build updates

Official builds expire **90 days after their build timestamp**. The persistent user timer checks daily with up to 30 minutes randomized delay. It fetches https://soloist-builds.spotifycdn.com/soloist_release_x86_64.tar.gz over HTTPS, rejects unsafe/oversized archive entries and non-official redirects, runs the staged executable's version check, and compares platform/build timestamps. Spotify does not provide a publisher signature in this flow; these checks are **not cryptographic publisher-signature verification**.

Updates are deferred if music is playing, playback state is unknown, or service state changes while staging. A paused active service is restarted and checked for readiness and restoration of its prior login. An inactive service stays inactive. One previous binary is retained for rollback; an expired binary is never deliberately restored. Offline/update failures keep the current binary and report failure for a later retry. Downloads, rollback and readiness checks have time limits.

```sh
systemctl --user start ii-soloist-update.service
systemctl --user list-timers ii-soloist-update.timer
journalctl --user -u ii-soloist.service -u ii-soloist-update.service
```

Non-secret update status is saved to `~/.local/share/spotify-sidebar/update-status.json`. Desktop notifications report failures/rollback and <=14-day expiry when `notify-send` is available; the journal/status remain authoritative. A service failure also triggers a desktop notification. No mechanism guarantees updates while the computer is off or permanently offline.

The prior executable is `~/.local/share/spotify-sidebar/soloist/soloist.previous`. Automatic rollback checks its lifetime and daemon health. For manual recovery, stop the service while paused, check the previous binary's `--version` timestamp is within 90 days, copy it to a temporary file in the same directory, atomically rename that to `soloist`, and restart the service. Keep the paired data untouched. Do not restore an expired build.

## Disable without deleting credentials

```sh
systemctl --user disable --now ii-soloist-update.timer ii-soloist.service
```

Stop an already-running update job separately with `systemctl --user stop ii-soloist-update.service` if necessary. Disabling preserves credentials, paired data and caches. Runtime binaries/caches and API keys are never part of this repository.

## Verification

```sh
python -m unittest discover -s tests -v
systemd-analyze --user verify dots/.config/systemd/user/ii-soloist*.service dots/.config/systemd/user/ii-soloist-update.timer
```

Tests use fake credentials/executables with temporary homes and simulated network/service boundaries; live checks use the user's actual paired Soloist. Enabling startup can be checked immediately, but actual reboot behavior should only be claimed after a reboot test.
